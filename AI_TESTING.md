# Вводная для ИИ: сценарии в браузере

Задание для языковой модели, которая дописывает проверки в своём форке.
Файл самодостаточный: его можно отдать модели целиком, ничего не объясняя
дополнительно. Человеку удобнее `e2e/README.md` — там то же самое, но с
объяснениями, почему прогон устроен именно так.

Агенты с доступом к репозиторию (Codex, Claude Code, Cursor, Copilot)
находят этот файл через `AGENTS.md` в корне сами. В окне чата — см. последний
раздел.

## Что от тебя нужно

Добавлять сценарии Playwright в `e2e/specs/*.spec.ts` и держать
`npm run e2e` зелёным.

Менять что-либо вне `e2e/**` не нужно. Если сценарий не проходит из-за
поведения приложения — это находка: опиши её в PR и оставь тест падающим или
помеченным `test.fixme`, но **не правь `src/**`, чтобы тест позеленел**.

## Один раз на машине

```bash
npm ci
npm ci --prefix e2e/mock-server
npx playwright install chromium
```

## Цикл работы

```bash
npm run e2e                                  # сборка против мока + все сценарии
npx playwright test e2e/specs/breaks.spec.ts # только один файл, сборка уже есть
npx playwright test -g "перерыв"             # по имени сценария
npx playwright show-report                   # разбор падения: шаги, трасса, скриншот
```

`npm run e2e` — единственная команда, которая должна проходить. Её же гоняет
CI (`.github/workflows/ci.yml`) на каждый push в любую ветку и на каждый PR;
при падении в артефактах сборки лежит `playwright-report`. Пока работаешь
только в `e2e/**`, приложение пересобирать не обязательно — хватает
`npx playwright test`; `npm run e2e` пересобирает всегда и потому медленнее.

Готовность к запуску проверяется одним признаком: `3 passed` (или больше)
и код возврата 0.

## Правила, без которых сценарии ломаются

1. **Ничего не ходит в сеть.** Приложение и API отвечают с одного адреса
   `http://localhost:4173`: статику отдаёт `e2e/static-server.mjs`, запросы
   `/api/**` он проксирует в мок. Внешние адреса фикстура закрывает. Не
   обращайся к боевому хосту и не поднимай приложение на другом порту: часы
   приложения сверяются по заголовку `Date` ответа, а с чужого origin браузер
   его не отдаёт — любой перерыв станет нулевым.
2. **Время двигает мок, не `sleep`.** `await advanceClock(page, 20 * 60)` —
   «прошло 20 минут». Функция сдвигает часы мока и перезагружает страницу:
   экран заказа сам ничего не опрашивает и без перезагрузки сдвига не
   заметит. Ожиданий вида `waitForTimeout` в сценариях быть не должно.
3. **Состояние сбрасывается перед каждым сценарием.** `await mock.reset()` в
   `test.beforeEach` заново заводит демонстрационный заказ `DEMO_ORDER_ID`,
   работа по нему уже начата. Сценарии идут по одному (`workers: 1`),
   общий мок этого требует.
4. **Вход — через фикстуру.** Пользуйся `nannyPage` из `e2e/fixtures.ts`:
   обычная авторизация идёт по коду из СМС и на моке не поднимается.
5. **Селекторы.** Тексты блока перерывов (`src/components/order/Breaks/texts.ts`)
   всегда русские — их брать можно. Остальной интерфейс переводится справочником
   тенанта и сейчас английский: «Завершить заказ» приезжает как «Close Drive».
   Для таких кнопок бери классы: `.order_break-btn`, `.order_take-order-btn`,
   `.breaks-confirm_actions button`. Во время перерыва кнопок
   `.order_take-order-btn` две: сначала «Продолжить работу», затем завершение
   заказа.

## Шаблон сценария

```ts
import { test, expect, mock, advanceClock, DEMO_ORDER_ID } from '../fixtures'

test.beforeEach(async () => {
  await mock.reset()
})

test('короткое имя сценария по-русски', async ({ nannyPage: page }) => {
  await page.goto(`/driver-order/${DEMO_ORDER_ID}`)

  await page.locator('.order_break-btn').click()
  await page.locator('.breaks-confirm_actions button').first().click()
  await expect(page.locator('.breaks_state-label')).toHaveText('Перерыв')

  await advanceClock(page, 20 * 60)

  // Состояние на стороне API, когда его надо сверить с экраном
  const orders = await mock.orders()
  expect(orders).toBeTruthy()
})
```

## Что стоит добавить, по убыванию ценности

Уже покрыто в `e2e/specs/breaks.spec.ts`: перерыв начат и завершён; короткий
перерыв мимо списка, но в суммах (п. 20 ТЗ); заказ завершён во время перерыва.

Не покрыто:

1. отказ начать второй перерыв, когда один уже идёт (п. 14 ТЗ);
2. несколько перерывов подряд и итоговая сводка по ним;
3. заказ без перерывов: блок не должен показывать ничего лишнего;
4. сверка плана и факта в итоговой таблице, отклонения со знаком;
5. пересчёт стоимости по оплачиваемому времени (п. 11 ТЗ).

## Если запустить прогон у себя нельзя

Локальный checkout не обязателен: сценарии умеет гонять CI, и ровно той же
командой `npm run e2e`. Прогон настоящий — на чистой машине, со сборкой,
браузером и моком; результат можно перепроверить по ссылке на прогон.

### Сначала — свой форк

Работать нужно **в своём форке**: в чужом репозитории у подключённого GitHub
только чтение, ветку там не создать. Кнопка Fork на странице репозитория,
дальше всё происходит под своей учёткой.

Две вещи, которые в форке делаются один раз:

- **включить Actions.** В форках GitHub держит их выключенными: вкладка
  Actions → «I understand my workflows, go ahead and enable them». Без этого
  коммит не запустит ничего;
- **pull request открывать внутри своего форка** (из своей ветки в свою
  `master`). У pull request'а, направленного в чужой репозиторий, прогон идёт
  с правами только на чтение: сценарии отработают, но комментарий с итогом не
  придёт — придётся смотреть Summary.

### Через коммит: цикл без единой команды на своей машине

1. положить файл сценария в `e2e/specs/` своей ветки — через веб-интерфейс
   GitHub («Add file» → «Create new file»), клонировать репозиторий не нужно;
2. открыть pull request в своём форке;
3. дождаться сборки: она ставит зависимости, поднимает мок, собирает
   приложение и прогоняет сценарии;
4. прочитать итог — он приходит **комментарием к pull request**: статус и
   последние 60 строк вывода прогона, включая упавшие ожидания. То же самое
   лежит на странице сборки в разделе Summary. Скачивать артефакты не нужно,
   отчёт Playwright прикладывается только на случай разбора трассы.

Правки сценария — новый коммит в ту же ветку, комментарий обновляется на
месте. Прогон герметичен: ходит только в собственный мок, боевой сервер и
сеть не нужны, поэтому результат на раннере тот же, что был бы локально.

### Через запуск руками: когда нужен один файл

Actions → «Тесты» → «Run workflow»: выбрать ветку и, если нужен не весь
набор, указать файл или имя сценария в поле ввода — это то же самое, что
`npx playwright test <файл>` локально. Пустое поле — прогоняется всё.
Итог такого запуска читается в разделе Summary у прогона: комментарий
приходит только к pull request, комментировать тут нечего.

### Через Codespaces: если нужна настоящая консоль

Code → Codespaces → «Create codespace on feature/e2e-playwright». Поднимется
браузерная среда по `.devcontainer/devcontainer.json`: node 22, зависимости и
браузер ставятся сами, порты проброшены. Дальше работают все команды из
раздела «Цикл работы», включая `npx playwright show-report` — отчёт
открывается в браузере через проброшенный порт. Это на случай, когда нужно
поковыряться руками; для проверки сценария хватает первых двух способов.

## Если сценарии пишет модель в окне чата

У чата нет доступа к репозиторию, поэтому один раз в начале разговора дайте
ему три файла:

1. **этот файл целиком** — правила и шаблон;
2. `e2e/fixtures.ts` — что вообще доступно сценарию;
3. `e2e/specs/breaks.spec.ts` — образец стиля и селекторов.

Дальше просите по одному сценарию за раз: один `test(...)`, а не файл
целиком — так проще понять, какая проверка сломалась. Готовый сценарий
кладите в `e2e/specs/`, запускайте `npm run e2e`.

При падении отдавайте модели **вывод прогона целиком**, а не пересказ:
Playwright печатает и ожидание, и то, что нашлось на странице, — по этому
тексту причина видна сразу, а по описанию словами обычно нет. Если падение
непонятное, `npx playwright show-report` покажет шаги, скриншот и трассу.
