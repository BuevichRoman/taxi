# Сценарии в браузере: как их писать и гонять

Вводная для того, кто будет дописывать проверки. Версия для ИИ, без
объяснений и пригодная к передаче целиком, — `AI_TESTING.md` в корне
репозитория (агенты приходят к ней через `AGENTS.md`).

Прогон идёт против мока API, без боевого сервера и без ожидания реального
времени.

## Быстрый старт

```bash
npm ci
npm ci --prefix e2e/mock-server
npx playwright install chromium

npm run e2e          # сборка против мока + все сценарии
```

Отдельные команды, когда сборка уже готова:

```bash
npx playwright test                      # все сценарии
npx playwright test --ui                 # с интерфейсом, удобно отлаживать
npx playwright test e2e/specs/breaks.spec.ts:25
npx playwright show-report               # отчёт после падения
```

Пересобирать приложение нужно после каждой правки исходников:

```bash
REACT_APP_SERVER_URL=http://localhost:4173 npm run build
```

## Как всё устроено

| Часть | Что делает |
|---|---|
| `e2e/mock-server` | API вместо боевого: заказы, перерывы, справочники, часы |
| `e2e/static-server.mjs` | отдаёт собранное приложение и **проксирует `/api/**` в мок** |
| `e2e/fixtures.ts` | вход в приложение, подмена справочников, управление часами |
| `e2e/specs` | сами сценарии |
| `playwright.config.ts` | поднимает оба сервера перед прогоном |

Три вещи, из-за которых прогон устроен именно так:

1. **Один адрес для приложения и API.** Статика и `/api/**` отвечают с
   `localhost:4173`, как и на бою, где приложение и API живут на одном хосте.
   Иначе браузер не отдаёт приложению заголовок `Date` ответа, а по нему
   сверяются часы (`src/tools/serverClock.ts`) — перерыв на экране остался бы
   нулевым, сколько бы времени мы ни прокрутили.
2. **Вход без формы.** Обычная авторизация идёт через код из СМС и на моке не
   поднимается. Фикстура кладёт токены мока в `localStorage`
   (`state.user.tokens`), приложение их подхватывает.
3. **Справочники тенанта.** Приложение грузит их отдельным скриптом с боевого
   хоста — адрес зашит в `src/config.ts`. Фикстура подменяет этот скрипт
   срезом из мока, а остальные внешние адреса закрывает: прогон не должен
   зависеть от сети.

## Управление временем

Часы двигает мок, приложение узнаёт о сдвиге из заголовка `Date`. Экран
заказа сам ничего не опрашивает, поэтому после сдвига нужна перезагрузка —
её делает `advanceClock`:

```ts
await advanceClock(page, 20 * 60)   // «прошло 20 минут»
```

`mock.reset()` возвращает мок в исходное состояние и заново заводит
демонстрационный заказ `1` — работа по нему уже начата. Он вызывается перед
каждым сценарием.

## Селекторы: что стабильно, а что нет

Интерфейс переводится, и язык сервиса приходит из справочника тенанта —
сейчас это английский. Поэтому:

- **тексты блока перерывов брать можно**: они лежат в
  `src/components/order/Breaks/texts.ts` и показываются по-русски, пока в
  справочнике нет ключей `wab_*`;
- **остальные надписи — нет**: «Завершить заказ» приезжает как «Close Drive».
  Для таких кнопок берите классы: `.order_break-btn`, `.order_take-order-btn`,
  `.breaks-confirm_actions button`.

Осторожно: во время перерыва кнопок `.order_take-order-btn` две — сначала
«Продолжить работу», затем завершение заказа.

## Что уже покрыто

`e2e/specs/breaks.spec.ts`:

1. няня уходит на перерыв и возвращается к работе — статус, счётчик, список;
2. короткий перерыв (меньше `min_visible_break_duration`) не попадает в
   список, но входит в суммы — п. 20 ТЗ;
3. заказ завершён во время перерыва — перерыв закрыт, показан итог.

## Что стоит добавить

- несколько перерывов подряд и итоговая сводка по ним;
- отказ начать второй перерыв, когда один уже идёт (п. 14 ТЗ);
- заказ, у которого перерывов не было: блок не должен ничего показывать;
- сверка плана и факта в итоговой таблице (отклонения со знаком);
- пересчёт стоимости по оплачиваемому времени (п. 11 ТЗ).

## Чего этим прогоном не проверить

Сторона заказчика — это Telegram-бот, у него интерфейса нет. Его сценарии
живут в репозитории бота и гоняются через `TestAdapter`, вводная там своя.
